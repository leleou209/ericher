# 会话后台运行与断联恢复

## 当前行为

- 独立场屋切换和新建草稿只改变当前视图，不调用停止 API。旧场屋继续执行；新草稿不继承旧场屋的忙碌状态。
- 停止按钮和 Esc 仍显式停止当前任务。自动导航、网络断开和提问卡提交失败不能替用户决定停止。
- 网络关闭时终止失联的本地 reader，不取消服务端任务。禁用 PartySocket 离线操作队列，避免重连补发旧 submit/cancel 帧；接通后使用 SDK 原流恢复协议。
- 提交前同时核验 socket OPEN、身份确认和房间名。未接通时保留草稿，不静默排队。SDK 异步准备阶段失败时也会在原场还原文字草稿。
- 服务端 `ChatIngress` 在 SDK 替换历史和启动模型之前登记提交。用户提交按消息 ID 去重，显式重新生成按请求 ID 去重；相同正文但不同消息 ID 是合法的新消息。重复提交同步权威历史并恢复原流，不另启一轮。
- 提问卡的成功作答登记持久收据。响应丢失后重试同一答案仍确认成功，不重复 resolve；冲突答案、过期卡和网络错误都不会自动变成普通新消息。
- UI 从服务端 start/resume/done 协议确认忙碌状态，避免 SDK observer 与恢复 reader 并存留下永久 busy。回放追到实时进度的 `replayComplete` 不是任务完成。

## 保留的边界

旧会话可能共用目录屋中的同一份历史。旧屋正在执行时，替换为另一份旧历史仍不安全，因此前后端均拒绝这种切换，但不会取消原任务；可以转到独立场屋，或等待旧任务完成。此修复没有自动迁移旧会话数据。

提交收据和作答收据保留 30 天；用户消息即使收据过期，仍可通过当前权威历史的消息 ID 防重。此机制防止重复的聊天提交，不声称为进程崩溃、外部工具结果不确定或第三方 API 提供全局 exactly-once。结果不确定时不撤销提交认领，应先核对原任务，确需重做再显式重新生成。

## 本轮补的四处并发与恢复缺口

上面几条协议原本是齐的，但内联实现漏了参照版补上的四道闸，2026-10-19 一并补上：

- `fireReminder` 加在途 id 集合：durable queue 重投与实例重建补投同一条时只投一次（「已投递」要等说完话才落账，挡不住这个窗口）。
- `flushSays` 两次唤醒共用一次投递：并发各自读一遍 pending 会把同一批话连说两遍。
- `scheduleReminder` 业务行写失败时撤销刚建好的调度，不留指向不存在 id 的孤立任务。
- 叫停监听改挂在流建起来之后，并在 onFinish/onError 摘除：预先叫停的轮次当场补记死因，轮次结算后才飘来的 abort 不再改写已结算的 `turnCapture`。

前端两处同属这条链路：切场保险丝（30 秒）卸载时清理、且按 ref 读最新的恢复闭包，避免按叫停那一刻的旧场域 park 草稿；停滞检测的依赖改回数组本身，弱网下一条长回复持续增长不再被误报成「停滞了」。

## 回归验证

常规检查：

```bash
npm run check
```

该命令依次执行类型检查、单测、生产构建、首屏包守卫（`scripts/check-startup-bundle.mjs`：首屏不得静态包含聊天与设置模块、入口 CSS 必须内联、JS 未到时要有启动与重试入口）。

隔离的真实 workerd / SQLite / WebSocket 回归：

```bash
npm run test:chat-recovery
```

该脚本只使用本地假模型和可计数假工具，不配置外部模型密钥；生成独立 `.wrangler/chat-recovery-test-*` 配置、状态和日志。默认端口为 8792，可用 `CHAT_TEST_PORT` 指定其他未占用端口。结束或失败时停止自己创建的进程树，不触及其他开发服务。测试入口限制 localhost，不用于部署。

覆盖：断开连接后原任务继续、另一个房间并行完成、重复消息只执行一次假工具、重连回放原流，以及显式取消仍生效。单元测试另覆盖真实 SQLite 防重、实例重建、失败结果不确定时保留收据、提问卡幂等、连接就绪及恢复状态转换，以及记忆注入的权限早退（`test/chatMemoryBlocks.test.ts`）。

2026-10-19 本地完整检查通过：76 个测试文件、995 项测试；类型检查、生产构建与首屏包守卫通过；`npm run test:chat-recovery` 与 `npm run test:weak-network` 在隔离 workerd 上通过。本轮只改本地，未部署，也未调用付费模型。
