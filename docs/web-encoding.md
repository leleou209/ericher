# 搜索与网页读取编码核查

## 核查结论

2026-10-15 核查确认：`src/tools/search.ts` 的网页直连使用 `Response.text()`。该接口固定按 UTF-8 解码，不识别 HTTP 或 HTML 声明的 GB2312/GBK。因此传统编码的中文页会生成替代字符 ``。正文超过 200 字又会被视为直连成功，使备用渲染路径不再执行。问题由真实 GBK 字节回归复现，修复前该测试失败。

不能据此断言所有中文新闻站都不可读：UTF-8 页面不受这一编码错配影响；受影响的是传统编码页及其他非 UTF-8 文本响应。未提供原央广网文章 URL，本次没有宣称已核验同一篇线上文章。

## 影响矩阵

| 路径 | 核查结果 | 本轮处理 |
| --- | --- | --- |
| `read_url` 直连正文 | 直接受影响；长乱码被当正文 | 按原始字节和字符集解码，损坏文本进入原有备用链路 |
| `browse` 正文、标题、链接文字 | 同用直连，均受影响 | 同一解码器，标题/正文/锚点文字均检查 |
| DuckDuckGo HTML / lite 搜索 | 同样使用固定 UTF-8；正常服务一般为 UTF-8，存在同类隐患 | 根据最终响应声明解码，保留现有端点和百科备用路径 |
| Tavily / Brave 搜索 JSON | 标准 JSON 按 UTF-8，未发现同一原始字节解码缺陷 | 保留 JSON 解析；上游已返回明显损坏标题/摘要时拒绝并退到免费搜索，明确说明原因 |
| Tavily extract | 标准 JSON 正常，但上游正文可能早已损坏 | 明显损坏的 `raw_content` 不再直接成功，继续直连/渲染备用链路 |
| 维基搜索、DDG 即时问答 JSON | 未发现同一原始字节缺陷 | 保留 JSON 解析，增加明显损坏结果保护 |
| Browser Run | Chromium 负责原始页面编码；`page.content()` 已是 Unicode | 无重复转码；对抽取后的明显损坏正文增加保护 |
| Jina Reader | 接收第三方文本，通常 UTF-8；原站解码由 Jina 负责 | 对返回文本使用同一响应解码和损坏检查，不尝试逆向恢复已损坏 Unicode |
| 图片下载 | `publicFetch` 后读取 `arrayBuffer()` | 不改二进制、不改逐跳 SSRF 校验 |
| 模型流、语音/天气专用接口、内部记忆检索 | 不是任意新闻 HTML 解码路径 | 不将其 UTF-8 协议改为 GBK，不扩展为无关文件转码 |

目前仅发现 `read_url` 在生产源码中调用 `fetchPageText`。关于“盯梢共用”的注释不能替代调用证据，因此本次不宣称存在另一条已验证的盯梢网页入口。主屋、独立场屋和允许联网工具的来客统一注册 `searchTools`，同一工具实现不会因身份不同而避开此问题。

## 修复策略与边界

新增 `src/shared/webText.ts`：优先使用 BOM，其次 HTTP `Content-Type` 的 charset，再识别 HTML 头部前 1024 字节的 meta charset / http-equiv，未声明时严格按 UTF-8 解码。支持 Workers 实际实现的 GB2312（WHATWG GBK 别名）、GBK、GB18030、Big5、UTF-8、UTF-16 等。HTTP 声明优先于 meta，普通 text/plain 正文中的 meta 不作为声明。

缺少声明且不是合法 UTF-8、声明未知字符集、或字节截断时，抛出可说明的错误并进入既有备用路径，不盲猜 GBK，也不默默插入替代字符。备用路径仍全部失败时，错误保留直连的编码失败原因。

第三方已经返回的 Unicode 无法可靠还原为原始中文。保护采用保守启发式：至少 3 个 `` 且占非空白字符的 1% 以上才认定为明显损坏；避免误伤正常文章偶尔解释这个符号的情况。它不能保证检测所有乱码，例如没有替代字符的二次转码中文仍可能无法自动识别。

## 下游与历史影响

乱码可能使模型漏掉指标名称、时间、单位、比较基准和正负方向，也可能污染后续摘要、笔记、报告或明确保存的记忆。数字和百分号仍可见不等于对应事实可信，不能只摘数字绕过核对。

本轮未读取或批量修改线上历史、笔记和记忆，也不能量化已有污染范围。需要清理时应先确定具体消息和引用来源，重新获得可靠原文后逐条核对，不对旧记录自动做替换字符“修补”。
